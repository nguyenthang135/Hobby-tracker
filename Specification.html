01 — Scope and approval status

Product goal: Help university students start and maintain hobbies by creating their own interests, scheduling practice, using an activity-focused timer with notes, and connecting with supportive peers.

Approved screen directions: Home V4 scheduling, Home V5 Hyper Mode, My Hobbies custom creation with the V3 visual icon picker, Community with chats, Settings V1, and simulated authentication. Sign Out appears only in Settings.

Prototype implementation: Standalone client-side HTML/CSS/JavaScript; shared data in browser local storage when supported. Users can try flows without paying for design tools. The site has no backend, service authentication, real chat transport, notifications, or email delivery.

Important formal-lab conflict: The uploaded PRM323 Lab 2 instructions require Google Stitch, exactly six Figma pages, a GitHub handoff repository, evidence logs, and a working Figma prototype. An HTML-based alternative needs explicit instructor approval. The separate UI Simplicity checklist does not replace those requirements.

Review state: Functionality smoke-tested in a browser; 20-point scoring is intentionally left blank until a person performs each criterion on each screen. No automatic 85/100 or accessibility certification is claimed.

Situation: Plays guitar but loses time to competing demands and social media.

Proposed measurable success criteria

These are validation targets, not results: complete first custom-hobby creation in ≤ 60 seconds; schedule a practice session in ≤ 45 seconds; save Hyper Mode time and notes without losing information; navigate from a community group to its chat in ≤ 3 actions.

Only top-level Home, Community, My Hobbies, and Settings appear in the bottom navigation. Authentication appears separately. Sign Out is located at the bottom of Settings, never on the Home screen.

04 — Three primary user flows

Flow 01 — Discover by creating a hobby (Minh)

Login→My Hobbies→Create Hobby→Icon + Color + Priority→Saved Collection
Recovery branch: Missing name or priority → visible validation → return to form; duplicate name → user edits the name, with existing hobby unaffected.

Flow 02 — Plan, practice and reflect (Khoa)

Home→Schedule→Hyper Mode→Timer + Tools + Notes→Finish→History
Alternative: No hobby exists → create a hobby first. Pause and resume are non-destructive. Exiting may pause the timer according to Settings. Existing schedules survive a priority change.

Flow 03 — Find a social connection

Community→Groups / People→Join / Message→Chat→Send
Alternative: Explore Activities → RSVP → optional Add to Home. RSVP alone does not schedule anything. Demo chat messages only update local state.

Interaction invariants

  • Hobbies must be created by users; there is no predefined selection catalog.
  • Every created hobby can be Active or Interested; both support all scheduling and Hyper Mode actions.
  • Priority updates never cancel existing sessions or delete history.
  • Calendar lists same-day items in ascending start time.
  • Finishing Hyper Mode saves a duration and notes snapshot in Home history.
  • External tools open a separate website; label them as shortcuts, never connected accounts.
  • RSVP never creates a Home activity until the user explicitly chooses Add to Home.
  • Sign Out only in Settings and requires confirmation.

Responsiveness and accessibility review

Target mobile widths: 360dp and 412dp; keep 48×48dp touch targets and ≥14sp content text wherever possible. The week selector is horizontally scrollable on narrower screens so day targets remain large. Verify normal-text contrast ≥4.5:1 (WCAG 2.x AA, subject to exceptions). Support focus indication, explicit states, and reduced-motion preferences. Inspect actual device rendering before certification.

07 — Data model, persistence and functional limits

Profile { name, handle, bio, color } Hobby { id, name, description, icon, color, priority } Schedule { id, hobbyId?, eventId?, date, time, duration, title, done } ActivityRecord { id, hobbyId, hobbyName, color, icon, date, ms, notes } Post { id, user, hobby, text, likes, liked, comments[] } Group { id, name, hobby, desc, members, joined } Event { id, title, hobby, date, time, going, scheduled } Chat { id, name, kind: Direct|Group, messages[] } Settings { music, search, reminders, autoTimer, pauseOnExit, dm, ... }

All collections share one local state object and are persisted to localStorage where the browser permits. Simulated authentication uses sessionStorage; passwords are deliberately not persisted. A focused-session draft may also be retained in session storage. Browser storage for locally opened files varies, so important data should not be treated as production-persistent.

Not implemented: Account security, backend persistence, real-time chat, Spotify OAuth or playback, image uploads, device notifications, offline synchronization, production moderation and access enforcement.

08 — Flutter handoff outline

The original lab requires six specific pieces for every screen: layout, components, states, interactions, navigation, and UI constraints. The screen matrix above and notes here provide a starting point but are not a full Flutter handoff yet.

Routing pattern

Start at /auth/login; successful demo sign-in routes to /home. Nested routes include /hobbies/:id, /home/hyper, /community/chat/:id, and Settings subsections.

Shared state

Use an application-level state store to share hobbies, schedules, Hyper Mode records, communities, chats and user settings. Never duplicate hobby data in individual screens.

Responsive

At widths ≥600dp, show content in a centered max-width layout or a split-pane dashboard; keep controls touch accessible. Do not stretch every form edge-to-edge.

Timer accuracy

Record elapsed monotonic duration with pause/resume boundaries. Finishing writes one activity record and marks a linked plan complete without overwriting other records.

Suggested repeatable checks

5-second test

Show each screen for five seconds; ask an observer to identify what it is and the primary next action. Record task and answer without coaching.

Grayscale test

Temporarily display without color; check that selected tabs, priorities, error states, and call-to-action hierarchy remain legible and recognizable.

Reduction test

Remove one decorative paragraph or card at a time. Keep the removal when no task-critical information disappears or becomes harder to find.
